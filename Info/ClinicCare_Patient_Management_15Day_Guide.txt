Phase 1 — Software Idea Description
What is ClinicCare
ClinicCare is a desktop application (installed on the clinic's computer, works without internet) that manages everything a small clinic or
small hospital does in a day: registering a patient, checking their old records, writing a prescription, printing certificates, tracking whether
the patient actually took the medicine (compliance), reminding them of the next follow-up by SMS/call, booking appointments, and
recording the day's income and expenses.
In simple words: today the doctor writes in a paper file or register. Tomorrow the same patient comes and the file has to be searched by hand.
ClinicCare replaces that register. Type the patient's mobile number or name → the full history opens in one second — every visit, every
medicine, every test, every certificate, and how regularly that patient followed the treatment.
Why a Desktop Application (and not a website)
Works without internet — a clinic cannot stop working when the broadband is down.
Fast — the database sits on the same computer, so search and printing are instant even with 50,000 patients.
Data stays inside the clinic — patient data is sensitive; nothing leaves the machine unless the clinic wants a cloud backup.
Installed like any normal software — one ClinicCare-Setup.exe, double-click, done. No server, no monthly hosting bill.
Printer-friendly — prescriptions, certificates and receipts print directly to the clinic's existing printer.
Purpose
Replace paper patient files and the manual OPD register with one searchable system.
Give the doctor the patient's complete past history on screen before the patient sits down.
Measure treatment compliance in percentage — so the doctor knows who is actually taking the medicine and who is not.
Make sure no follow-up is missed — automatic due-list, notification, SMS and call list.
Print professional prescriptions and certificates on the clinic letterhead in one click.
Show the doctor exactly how much money came in and went out, daily and monthly.
Who will use it
User What they do in the software
Doctor Sees patient history, writes diagnosis, tests and prescription, records compliance, issues certificates, sees all reports
and income.
Receptionist Registers new patients, searches old patients by mobile/name, books appointments, manages the waiting queue,
collects fees and prints receipts.
Assistant / Compounder Enters vitals (BP, weight, temperature), makes follow-up calls from the call list, sends SMS reminders.
Owner / Admin Manages users and passwords, clinic letterhead, fees, backup, and sees income & expense reports.

Cut patient waiting time — old file search in 1 second instead of 5 minutes.

2.2 High-Level Architecture
ClinicCare is one installed application with three layers running on the same computer. The React screens talk to a local Node/Express API
on localhost, which talks to the SQLite file through Prisma. Because everything is local, there is no network delay and no internet
dependency — except the SMS service, which is the only part that goes outside.

2.5 The Compliance Percentage — exact formula
The client's sheet says "Percentage Compliance" but does not define it, so this document defines it precisely. The developer must
implement it in one place only: compliance.service.ts.
Medicine compliance % = (doses actually taken ÷ doses prescribed) × 100
Follow-up compliance % = (follow-ups attended ÷ follow-ups given) × 100
Overall compliance % = (Medicine % × 0.7) + (Follow-up % × 0.3) ← weights configurable in Settings
Grade: 80–100% → GOOD (green)
50–79% → AVERAGE (yellow)
0–49% → POOR (red)
Where the numbers come from: doses prescribed is calculated automatically by the software from the prescription (morning +
afternoon + evening + night) × number of days. Doses taken is entered by the doctor or assistant at the next visit — either by asking the
patient, or by a simple slider (100% / 75% / 50% / 25% / 0%), or by counting the returned tablets. Nothing is guessed by the software.
In simple words: if the patient was given 2 tablets a day for 10 days (= 20 tablets) and says he took only 12, the software shows 60% —
AVERAGE (yellow) on his record card forever. The doctor sees it at a glance on the next visit.

2.7 Security & Data Safety
Login is compulsory — username + password (bcrypt hashed), plus a 4-digit PIN for fast user switching at the counter.
Role-based access — the receptionist cannot open income reports or edit a diagnosis; the assistant sees only vitals, follow-up and
call list. Enforced on the API (roleGuard), not just by hiding buttons.
Auto screen-lock after X minutes idle — patient data is not left open on a counter screen.
Audit log on every create/edit/delete of a patient, visit, bill or certificate — stores who, what, before and after.
No hard delete of clinical data — records are only marked inactive/cancelled, so history is never lost.
Daily automatic backup of clinic.db to a local folder, plus a manual "Backup to pen-drive" button and optional cloud upload. Keep
last 30 backups.
Restore screen with a warning + confirmation, admin only.
Input validation twice — on the form (React Hook Form + Zod) and again on the API (Zod/class-validator), so bad data cannot enter
the database from any path.
Optional database encryption (SQLCipher) if the clinic wants the file unreadable even if the PC is stolen.
SMS API keys stored in the settings table / .env, never printed in the code or on screen.
2.8 Multi-computer option (reception + doctor cabin)
Most small clinics run on one computer. If two are needed (reception counter and doctor's cabin), no code rewrite is required: install
the API + SQLite on one computer (the "main" PC), and point the second computer's app to http://192.168.1.x:4000 over the clinic's
LAN/Wi-Fi. Only a setting changes. This is why the logic lives in a separate API layer instead of inside the screens — plan for it on Day 1,
switch it on whenever the clinic asks.
2.9 Development Strategy
Build vertically — finish one complete module per day (database table → API → screen → print/report) instead of building all
databases first. The app is demoable to the client every single evening.
Build the reusable components on Day 1–3 (DataTable, FormModal, SearchBox, PrintLayout) and reuse them everywhere — this is
what makes Days 8–14 fast.
All shared calculations (compliance %, totals, numbering) live in services, never copy-pasted into screens.
Use an AI coding assistant (Claude Code / Cursor) with the ready prompts in Phase 6, then review and test before moving on.
Show the doctor the screen on Day 3, Day 6 and Day 9 — real clinical wording (complaint names, certificate text, medicine
names) must come from the doctor, not from the developer's imagination.
Day 15 gets no new features — only testing, fixing, installer build and installation at the clinic.

Correctness & safety review (clinical data)
Compliance % was undefined in the requirement — now defined with an exact formula in 2.5 and implemented in one shared service,
so the number can never differ between two screens.
Doses prescribed is auto-calculated from the prescription, not typed — removes the biggest source of wrong percentages.
Prescription printing must show before/after food and timing in words (not codes like "1-0-1"), because the patient reads it. Both
are printed.
Allergy and chronic-disease flags appear as a red banner at the top of the prescription screen — a safety feature, not a nice-to-have.
No hard delete of clinical records; edits are audit-logged. Certificates once printed can be cancelled but not silently changed.
Performance & growth
SQLite with proper indexes on mobile, name, patientId, visitDate handles 1–2 lakh patients and 10 lakh visits on ordinary clinic
hardware. This is far beyond a small clinic's 15-year volume.
Search is debounced and paginated — the app never loads the full patient table into the screen.
If the clinic later grows to multiple branches, the same API + Prisma code points at PostgreSQL/MySQL on a server with a connectionstring
change — the schema does not change.
Alignment with the doctor's real working style
The whole prescription flow must be completable with the keyboard only — a doctor will abandon software that needs the mouse for
every field. Tab order and shortcuts are a Day 6 requirement, not polish.
"Repeat last prescription" in one click covers the majority of chronic follow-up visits.
The receptionist's search box accepts mobile number first — that is how Indian clinics actually identify a returning patient. Exactly
as written on the client's sheet.

Day 1–2 block everything — no screen can be built or tested before login, layout and clinic profile exist.
Day 3 (Patient) blocks Days 5–12 — a visit, prescription, certificate, follow-up and bill all need a patient to exist first.
Day 4 (Medicine) blocks Day 6 — a prescription cannot be written without the medicine list.
Day 5 (Visit) blocks Days 6, 8, 9, 11, 12 — prescription, compliance, follow-up, certificate and bill are all attached to a visit.
Day 6 (Prescription) blocks Day 8 — compliance % is calculated from the prescribed doses, so the prescription must exist and be
correct first.
Day 8 & 9 are placed together — compliance is recorded during a follow-up, so building them back-to-back avoids rework.
Day 13 (Dashboard) comes near the end deliberately — it only summarises data produced by Days 3–12; building it earlier means
rebuilding it later.
Day 14 (Roles) is applied last on purpose — locking permissions before all screens exist slows down daily testing.
Day 15 has zero new features by design — a hard scope freeze so that something working is definitely installed at the clinic.
Client checklist before Day 1 (please arrange these): clinic letterhead / logo file • doctor's full name, degree and registration number • the
exact wording of the certificates currently issued • current fee list • a list of commonly prescribed medicines (Excel or photo of the list) • the old
patient register in Excel, if any • SMS gateway account (if SMS is wanted) • the computer and printer the software will run on.

Phase 5 — Roadmap Audit
Completeness
Every module from the Phase 1 feature list is scheduled on a specific day. Cross-checked against the requirement-mapping table — all
12 client points covered, none left floating.
Efficiency
Reusable components (DataTable, FormModal, SearchBox, PrintLayout) are built on Days 1–3 and reused by every later screen —
this roughly halves the work from Day 7 onward.
Shared services (NumberService, ComplianceService, PrintService, NotificationService) are written once and injected everywhere —
no duplicated logic, so a fix applies everywhere at once.
One HTML print template system serves prescription, certificate and receipt — only the body changes, the letterhead is shared.
Dependency check
No day needs a table, service or screen that an earlier day has not created — verified line-by-line against the dependency list in Phase
4. The build order is safe.
Risk and buffer
Highest-risk days: Day 6 (Prescription) and Day 8 (Compliance). Day 6 is the most-used screen in the clinic and must be
keyboard-fast and print perfectly; Day 8 contains the only non-obvious calculation in the product. If the project slips, protect these two
days first.
Second risk: Day 10 (SMS) — it depends on an outside gateway, an account and a DLT-approved template, which can take days to
get approved in India. Apply for the SMS account on Day 1, not on Day 10. Build the module so it works with the sending switched
off.
Compressible days if behind schedule: Day 13 (Dashboard — charts can start simple) and parts of Day 10 (WhatsApp can be a
click-to-chat link instead of an API). These are additive, not foundational.
Day 15 is a fixed buffer — installer building, installation at the clinic and staff training always take longer than expected. Do not let
feature work eat into it.

A repeatable structure so that every prompt written for this project — not only Days 1–15 — produces consistent, on-specification code.
7.1 Standard prompt template
Act as a senior full-stack engineer working on ClinicCare
(Electron + React/Vite client, Node/Express API, Prisma + SQLite,
existing code and conventions from the previous days).
Context: (1-2 lines - what already exists that this task builds on)

- (concrete, testable points)
- (Prisma model changes, if any)
- (API routes: method, path, what it returns)
- (React screen behaviour, field by field)
- (which existing service it must call - NumberService, ComplianceService,
PrintService, NotificationService)
Constraints:
- Follow the existing folder structure and module pattern
- Reuse the existing shared components (DataTable, FormModal, SearchBox,
PrintLayout) - do NOT create duplicates
- Validate with Zod on the form AND again on the API
- Wrap any multi-table write in a Prisma transaction
- Apply roleGuard on every new route
- Never hard-delete clinical data - deactivate or cancel instead
- All money to 2 decimals; all dates stored and compared as local clinic dates

changed.
7.2 Reusable prompt patterns
Pattern Use it for Order to write it in
A — New module Patient, Medicine, Certificate, Expense … Prisma model → API route/controller/service → Zod validator → React list
screen → React form → print/export. Always this order, so each layer has
something real underneath it.
B — Shared calculation Compliance %, dose totals, bill totals State the formula in the prompt exactly, demand it live in ONE service file,
and ask for unit tests. Never let the same formula be written in a screen.
C — Print template Prescription, certificate, receipt Describe the paper size, every section top to bottom, exactly which fields
print, and what must print in words rather than codes. Ask for an HTML
template plus a preview screen.
D — Report Any report screen Specify the source tables, the filters, the grouping, the columns, the totals

produce the wrong grouping.
E — Retrofit across modules Applying roleGuard, audit log, branch/date
rules
List every existing file that must change and ask the assistant to show the
diff for each one, not a rewritten file.
F — Stabilisation (Day 15) Testing and fixing Give a checklist to walk through, not a feature to build — this is what stops
new features creeping into the last day.
7.3 Context management
Keep SCHEMA.md (all Prisma models) and API.md (all routes) in the repository and update them at the end of every day. Paste the
relevant few models into a prompt instead of the entire schema file.
Refer to earlier work by name — "the ComplianceService from Day 8", "the MedicineSearchInput from Day 4" — rather than pasting
the code again, when the assistant already has repository access.
In a fresh chat session, paste only the model definitions and function signatures the new task depends on.
Keep a DECISIONS.md file: every rule the doctor gives you (certificate wording, fee amounts, compliance weights) goes there, so it is
never lost between sessions.
7.4 Daily working rhythm
1. One day = one prompt = one tested commit. Never batch two days into one prompt.
2. After the code is generated, run the app and manually test the happy path plus one edge case before starting the next day.
3. Commit to git every evening — that is your rollback point if the next day's code breaks something.
4. If the output drifts from the plan, send a short correction prompt naming the specific requirement that was missed, instead of rewriting
the whole original prompt.
5. Show the doctor the screen on Days 3, 6, 9 and 12. Change wording and fields immediately — corrections are cheap on the day they
are found and expensive at the end.
